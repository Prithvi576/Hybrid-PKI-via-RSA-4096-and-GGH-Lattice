# Key Management
## Hybrid PKI–SCADA — Person 1 Sender

**Status:** As-implemented  
**Related documents:** [`tcp_protocol.md`](tcp_protocol.md)

---

## 1. Key Types and Algorithms

The sender uses two independent key pairs per machine identity:

| Key type | Algorithm            | Key size        | Signature size |
|----------|----------------------|-----------------|----------------|
| RSA      | RSA-4096 / PSS / SHA-256 | 4096-bit modulus | 512 bytes      |
| GGH      | GGH lattice hash-and-sign (educational) | n = 16 dimension | 128 bytes (16 × 8) |

Both signatures cover the same canonical message (see [`tcp_protocol.md §4`](tcp_protocol.md)).

## 2. Key Generation

### RSA-4096

Source: [`crypto/rsa/rsa_keygen.cpp`](../crypto/rsa/rsa_keygen.cpp)

- Generated via `EVP_PKEY_CTX_new_from_name(nullptr, "RSA", nullptr)` with
  `EVP_PKEY_CTX_set_rsa_keygen_bits(..., 4096)`.
- OpenSSL's CSPRNG (`RAND_bytes`) provides the randomness internally.
- The private and public handles both refer to the same in-memory `EVP_PKEY`
  object (ref-counted).
- Signing uses `EVP_DigestSign` with `EVP_sha256()` and RSA-PSS padding
  (randomized salt — each signature is different even for the same message).

### GGH (lattice-based)

Source: [`crypto/ggh/ggh_keygen.cpp`](../crypto/ggh/ggh_keygen.cpp)

- Dimension n = 16 (compile-time constant `kDimension`).
- **Private key (good basis):** 16 × 16 diagonal-dominated integer matrix.
  - Diagonal entries are fixed at 59.
  - Off-diagonal entries are random integers in \[−3, 3\] from `RAND_bytes`.
- **Public key (bad basis):** Computed as `U × R` where R is the private basis
  and U is a random unimodular matrix generated by 128 elementary row
  operations (each preserving det(U) = ±1).
- Signing is deterministic given the same message and key (uses
  `EVP_Digest` with SHA-256 to derive a target vector from the message).
- Verification uses Babai's round-off CVP algorithm against the public basis.

## 3. Key Storage — Current State

**Keys are NOT persisted to disk in the current implementation.**

Key pairs are generated at runtime and stored **in memory only** in the
`MachineKeys` struct, which is held in `MachineManager::keys_` (an
`unordered_map<string, MachineKeys>`).

Source: [`sender/machines/machine_manager.hpp`](../sender/machines/machine_manager.hpp)

```cpp
struct MachineKeys {
    std::unique_ptr<hybrid_pki::RSAKeyPair> rsa;
    std::unique_ptr<hybrid_pki::GGHKeyPair> ggh;
};
```

Keys are generated on demand via `MachineManager::keysFor(machine_id)` and
are lost when the application exits.

**Gap:** There is no serialization, file storage, or reload path for either
key pair.  This means:
- A new key pair is generated for every session.
- The receiver cannot verify signatures from a previous session without
  receiving the new public key out-of-band each time.
- There is no key rotation or revocation mechanism yet.

## 4. Public-Key Fingerprints

Both RSA and GGH public keys carry a `public_fingerprint` string that is
computed at keygen time.

| Key  | Fingerprint computation                                                |
|------|------------------------------------------------------------------------|
| RSA  | SHA-256 of the DER-encoded `SubjectPublicKeyInfo` blob; first 10 bytes printed as hex (20 hex chars) |
| GGH  | SHA-256 of the raw `int64_t[]` bad-basis array; first 10 bytes printed as hex (20 hex chars) |

Fingerprints are stored in `MessageRecord` fields `rsa_fingerprint` and
`ggh_fingerprint` alongside each sent message in local JSON storage
(`sender/storage/local_storage.cpp`).

**Note:** These fingerprints are only 10-byte truncations of SHA-256.  They
are suitable for display purposes and collision-resistant enough for
user-visible key identification, but they are not certificate-grade
identifiers.

## 5. Machine Identity and Key Association

Source: [`sender/machines/machine_manager.hpp`](../sender/machines/machine_manager.hpp),
[`sender/storage/local_storage.hpp`](../sender/storage/local_storage.hpp)

- Each machine is assigned a UUID-like string ID (`MachineRecord::id`).
- Machines are persisted to `machines.json` via `LocalStorage::saveMachines()`.
- Key pairs are associated with a machine by its `id` in `MachineManager::keys_`.

**Gap:** Machine records do **not** include serialized public keys.
The `machines.json` file stores `id`, `display_name`, `hostname`, `port`,
`created_utc`, and `last_activity_utc` only.

## 6. What the TCP Frame Currently Contains

See [`tcp_protocol.md §8`](tcp_protocol.md) for the authoritative list.

**Present in every frame:**

- The signed command string
- The UTC timestamp
- The monotonic sequence number
- The RSA-4096 signature (512 bytes)
- The GGH lattice-point signature (128 bytes, 16 coordinates)

**Not present in any frame:**

| Missing element | Why it matters |
|-----------------|----------------|
| Sender's RSA public key | Receiver cannot verify without it |
| Sender's GGH public key | Same |
| RSA key fingerprint | Receiver cannot select the correct stored key |
| GGH key fingerprint | Same |
| Sender machine ID | No in-band identity linking |
| Certificate or chain | No PKI trust chain in the frame |

## 7. Trust Model — Current Gaps

**Receiving a public key from an untrusted sender does not automatically
establish trust.**

The following questions are **open** and must be resolved in coordination
with **Person 2 (PKI / trust module)**:

| # | Question |
|---|----------|
| 1 | How does the receiver obtain the sender's RSA and GGH public keys? |
| 2 | Who certifies that a key belongs to a specific machine? |
| 3 | How does the receiver identify which stored key to use for a given connection? |
| 4 | How are compromised or rotated keys revoked? |
| 5 | Should the sender's machine ID be added to the TCP frame as a lookup token? |
| 6 | Should Person 1 serialize and persist key pairs so that a sender identity is stable across restarts? |

## 8. Smallest Compatible Integration Requirement (Proposal for Person 2)

Person 1's sender currently generates keys ephemerally.  The minimum change
required for end-to-end verification to work is one of:

**Option A — Out-of-band pre-registration (no protocol change needed):**  
Before any connection, the sender exports its current public keys (RSA DER +
GGH raw matrix) to a shared store.  The receiver loads them keyed by machine
ID.  The machine ID is communicated out-of-band (e.g. via configuration).

**Option B — In-frame key identifier (minor protocol extension):**  
Add one field to the TCP payload: `sender_id` (a short ASCII string, max
64 bytes).  Person 3's receiver uses this to look up pre-registered keys in
Person 2's trust store.  No public key bytes are transmitted in the frame;
trust is established by Person 2 before the connection opens.

**Person 1 will not modify the wire protocol unilaterally.**  The chosen
approach must be agreed with Person 2 (trust store design) and Person 3
(receiver implementation) first.

---

## 9. What Must Never Be Transmitted

- RSA private keys (`EVP_PKEY` private component)
- GGH private short-basis matrix (`GGHPrivateKey::short_basis`)

These are held only in the sender process memory and are never written to
disk or sent over the network.
